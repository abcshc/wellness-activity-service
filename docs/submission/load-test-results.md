# 건강활동 업로드 부하 비교 결과

## 목적

청크 단위 batch 저장 전후로 활동 업로드 API를 같은 조건에서 측정했습니다. 이 문서는 특정 개발 장비에서의 절대 성능을 주장하기보다, 구현 변경이 결과 계약을 유지하면서 지연·오류 경향을 어떻게 바꿨는지 남기기 위한 비교 기록입니다.

## 먼저 구분할 두 검증

| 구분 | 도구와 실행 방식 | 확인하는 것 | 확인하지 않는 것 |
| --- | --- | --- | --- |
| 요청 크기 통합 테스트 | JUnit + MockMvc + Testcontainers MySQL | 100·500·1,000개 항목의 저장 결과, 응답 계약, 최종 행 수 | 동시 사용자 수와 지속 처리량 |
| 동시 업로드 탐색 | k6가 별도 애플리케이션·MySQL 컨테이너에 실제 HTTP 요청 | VU 증가에 따른 응답 시간, 타임아웃, 오류율 | 운영 환경의 절대 TPS·SLA |

`VU`는 **Virtual User(가상 사용자)**의 약자입니다. 요청 횟수가 아니라, 부하 도구가 동시에 동작하게 만드는 사용자 수를 뜻합니다.

이번 탐색에서 가상 사용자 한 명은 1,000개 항목의 업로드 요청을 세 번 차례대로 보냈습니다. 따라서 10 VU는 “최대 10명의 사용자가 각각 1,000개 항목을 동시에 업로드하는 상황”을 흉내 낸 것입니다. 세 번씩 요청하므로 총 업로드 요청 수는 30건입니다.

## 검증 흐름

1. 먼저 요청 크기별 통합 테스트로 100·500·1,000개 항목이 모두 저장되는지 확인합니다. 이 단계는 처리량을 측정하지 않습니다.
2. 독립된 애플리케이션·MySQL 컨테이너에서 100개 항목을 먼저 저장해 업로드 경로를 warm-up 합니다.
3. 새 MySQL 볼륨에서 요청당 1,000개 신규 항목을 5·10·20·40 VU로 각각 실행합니다.
4. HTTP 오류율, 응답 시간, `createdCount`와 요청 항목 수가 같은지 확인합니다.

## 실행 조건

| 항목 | 조건 |
| --- | --- |
| 애플리케이션·MySQL | 각각 1 CPU, 1GiB 메모리 제한 |
| 애플리케이션 JVM | `-Xms256m -Xmx512m` |
| 부하 생성기 | 0.5 CPU, 512MiB 메모리 제한 |
| 입력 | 10분 구간의 신규 걸음수 이벤트 1,000개/요청 |
| provider | SamsungHealth, Health Kit, HealthConnect를 순환 |
| 요청 타임아웃 | 30초 |
| 지연 판정 | 업로드 p95 10초 미만 |
| warm-up | 측정 전 같은 API로 100개 항목을 한 번 저장하며, warm-up 요청은 결과에서 제외 |

## 무엇을 기준으로 판단하는가

한 가지 수치만으로 “잘 된다” 또는 “실패했다”고 판단하지 않습니다.

| 구분 | 확인하는 지표 | 의미 |
| --- | --- | --- |
| 기능 성공 | HTTP 오류율, 응답의 `createdCount`, 항목 검증 결과 | 요청이 저장 계약을 지켰는지 확인 |
| 지연 | 활동 업로드 p95 | 느려지기 시작하는 지점을 확인 |
| 타임아웃 | 업로드 요청 타임아웃 수 | 클라이언트가 응답을 기다리다 포기한 요청이 있는지 확인 |
| MySQL 상태 | 연결·실행 스레드, 최대 연결 수, slow query, InnoDB 락 대기 | 애플리케이션 지연과 DB 상태를 함께 비교 |

MySQL 상태값은 각 VU 단계의 실행 전후에 별도 파일로 기록합니다. 현재 단계에서는 애플리케이션의 HikariCP 내부 지표를 외부에 노출하지 않습니다. 배치 저장 적용 후에도 병목이 남는 경우에만, 접근 제어된 관측 프로필로 HikariCP 대기 지표를 추가합니다.

각 VU는 세 번 반복했습니다. 표본이 작기 때문에 아래 수치는 지속적인 성능 보장이나 운영 SLA가 아닙니다. 구현 변경 전후를 같은 조건에서 비교하기 위한 탐색 결과로만 사용합니다.

## 개선 전후 결과

| 최대 동시 VU | 업로드 요청 | 변경 전 p95 | 변경 후 p95 | p95 변화 | 변경 후 관측 요청률 | 변경 전 HTTP 오류 | 변경 후 HTTP 오류 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 5 | 15 | 5.95초 | 1.80초 | -69.7% | 3.80건/초 | 0 | 0 |
| 10 | 30 | 10.21초 | 2.86초 | -72.0% | 4.13건/초 | 0 | 0 |
| 20 | 60 | 19.40초 | 4.78초 | -75.3% | 5.48건/초 | 0 | 0 |
| 40 | 120 | 29.88초 | 8.60초 | -71.2% | 6.69건/초 | 7 | 0 |

변경 후 각 단계는 요청당 1,000개 신규 이벤트를 저장했고, 성공 응답의 `createdCount`는 모두 요청 항목 수와 같았습니다. 표의 요청률은 k6의 반복 횟수와 전체 실행 시간으로 계산한 관측값이며, 지속 부하에서 보장하는 TPS가 아닙니다. 40 VU의 120건 요청에서도 HTTP 오류와 30초 클라이언트 타임아웃은 없었습니다.

변경 전 기준선은 `63b364b`, 변경 후 측정은 `ffad606` 기준으로 실행했습니다. 두 실행 모두 동일한 컨테이너 자원, warm-up, 새 MySQL 볼륨, provider 순환, VU당 3회 반복을 사용했습니다. 변경 후 각 단계의 MySQL 전후 상태에서는 slow query와 InnoDB 락 대기가 모두 0이었습니다.

## 해석과 API 입력 기준

- 이벤트별 저장을 최대 200건의 multi-row `INSERT IGNORE`로 전환한 뒤, 모든 탐색 단계가 p95 10초 조건을 통과했습니다. DB 왕복 횟수를 줄인 효과로 해석할 수 있지만, 이 실행만으로 운영 환경의 처리량을 보장하지는 않습니다.
- 일반 동기화 endpoint는 한 요청에 **최대 1,000개 항목**을 허용합니다. 이 값은 100·500·1,000건 MySQL 통합 테스트와 이번 1,000건 동시 업로드 비교를 통과한 범위입니다.
- 과거 전체 이관은 별도 API나 비동기 Job을 현재 범위에 추가하지 않습니다. 클라이언트가 시간순으로 1,000건 이하 묶음을 **순차 전송**하고, 재시도 시에는 기존 멱등 업로드를 사용합니다. 이 방식은 현재의 원본 우선·재전송 무시 계약을 유지합니다.
- 더 큰 요청, 더 높은 동시성, 지속 부하를 지원해야 할 때는 같은 조건의 반복 횟수와 실행 횟수를 늘려 분산을 확인한 뒤 상한·청크 크기·비동기 이관 흐름을 다시 결정합니다.

## 관련 자동화 검증

- 요청 크기별 저장 계약: `ActivityUploadRequestSizeIntegrationTest`
- 원본 입력·재전송·Daily·Monthly 정합성: `ActivityWorkflowIntegrationTest`
- 업로드 입력·부분 성공 응답: `ActivityUploadControllerIntegrationTest`
- 동시 업로드 저장·집계 정합성: `ActivityUploadConcurrencyIntegrationTest`
