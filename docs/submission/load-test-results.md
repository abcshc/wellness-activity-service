# 건강활동 업로드 부하 탐색 결과

## 목적

활동 업로드 API가 큰 요청과 동시 요청을 받을 때 어떻게 동작하는지 확인했습니다. 이 문서는 특정 개발 장비에서의 절대 성능을 주장하기보다, 현재 구현에서 어느 구간부터 지연과 오류가 나타나는지 이해하기 위한 탐색 기록입니다.

## 먼저 구분할 두 검증

| 구분 | 도구와 실행 방식 | 확인하는 것 | 확인하지 않는 것 |
| --- | --- | --- | --- |
| 요청 크기 통합 테스트 | JUnit + MockMvc + Testcontainers MySQL | 100·500·1,000개 항목의 저장 결과, 응답 계약, 최종 행 수 | 동시 사용자 수와 지속 처리량 |
| 동시 업로드 탐색 | k6가 별도 애플리케이션·MySQL 컨테이너에 실제 HTTP 요청 | VU 증가에 따른 응답 시간, 타임아웃, 오류율 | 운영 환경의 절대 TPS·SLA |

`VU`는 **Virtual User(가상 사용자)**의 약자입니다. 요청 횟수가 아니라, 부하 도구가 동시에 동작하게 만드는 사용자 수를 뜻합니다.

이번 탐색에서 가상 사용자 한 명은 1,000개 항목의 업로드 요청을 세 번 차례대로 보냈습니다. 따라서 10 VU는 “최대 10명의 사용자가 각각 1,000개 항목을 동시에 업로드하는 상황”을 흉내 낸 것입니다. 세 번씩 요청하므로 총 업로드 요청 수는 30건입니다.

## 검증 흐름

1. 먼저 요청 크기별 통합 테스트로 100·500·1,000개 항목이 모두 저장되는지 확인합니다. 이 단계는 처리량을 측정하지 않습니다.
2. 독립된 애플리케이션·MySQL 컨테이너에서 100개 항목을 먼저 저장해 업로드 경로를 warm-up 합니다.
3. 새 MySQL 볼륨에서 요청당 1,000개 신규 항목을 5·10·20·40 VU로 각각 실행합니다.
4. HTTP 오류율, 응답 시간, `createdCount`와 요청 항목 수가 같은지 확인합니다.

## 실행 조건

| 항목 | 조건 |
| --- | --- |
| 애플리케이션·MySQL | 각각 1 CPU, 1GiB 메모리 제한 |
| 애플리케이션 JVM | `-Xms256m -Xmx512m` |
| 부하 생성기 | 0.5 CPU, 512MiB 메모리 제한 |
| 입력 | 10분 구간의 신규 걸음수 이벤트 1,000개/요청 |
| provider | SamsungHealth, Health Kit, HealthConnect를 순환 |
| 요청 타임아웃 | 30초 |
| 지연 판정 | 업로드 p95 10초 미만 |
| warm-up | 측정 전 같은 API로 100개 항목을 한 번 저장하며, warm-up 요청은 결과에서 제외 |

## 무엇을 기준으로 판단하는가

한 가지 수치만으로 “잘 된다” 또는 “실패했다”고 판단하지 않습니다.

| 구분 | 확인하는 지표 | 의미 |
| --- | --- | --- |
| 기능 성공 | HTTP 오류율, 응답의 `createdCount`, 항목 검증 결과 | 요청이 저장 계약을 지켰는지 확인 |
| 지연 | 활동 업로드 p95 | 느려지기 시작하는 지점을 확인 |
| 타임아웃 | 업로드 요청 타임아웃 수 | 클라이언트가 응답을 기다리다 포기한 요청이 있는지 확인 |
| MySQL 상태 | 연결·실행 스레드, 최대 연결 수, slow query, InnoDB 락 대기 | 애플리케이션 지연과 DB 상태를 함께 비교 |

MySQL 상태값은 각 VU 단계의 실행 전후에 별도 파일로 기록합니다. 현재 단계에서는 애플리케이션의 HikariCP 내부 지표를 외부에 노출하지 않습니다. 배치 저장 적용 후에도 병목이 남는 경우에만, 접근 제어된 관측 프로필로 HikariCP 대기 지표를 추가합니다.

각 VU는 세 번 반복했습니다. 표본이 작기 때문에 아래 수치는 지속적인 성능 보장이나 운영 SLA가 아닙니다. 현재 구조의 병목 후보를 찾고, 이후 개선 전후를 비교하기 위한 기준선으로 사용합니다.

## 결과

| 최대 동시 VU | 업로드 요청 | 이벤트 수 | HTTP 오류 | 업로드 p95 | 판정 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 5 | 15 | 15,000 | 0 | 5.95초 | 통과 |
| 10 | 30 | 30,000 | 0 | 10.21초 | 지연 조건 초과 |
| 20 | 60 | 60,000 | 0 | 19.40초 | 지연 조건 초과 |
| 40 | 120 | 120,000 | 7 | 29.88초 | 지연·기능 조건 초과 |

40 VU에서는 7건이 30초 안에 응답을 받지 못해 타임아웃으로 실패했습니다. 반대로 성공한 응답은 모두 요청 항목 수와 같은 `createdCount`를 반환했습니다.

## 해석과 다음 단계

- 현재 자원 제한에서는 p95 10초 기준의 성능 경계가 5~10 VU 사이에서 나타났습니다.
- HTTP 오류가 없더라도 응답 시간은 먼저 느려질 수 있습니다. 오류율만으로 상태를 판단하지 않는 이유입니다.
- 40 VU에서 타임아웃이 다시 나타났습니다. 현재는 항목마다 `INSERT IGNORE`를 실행하므로, DB 왕복·커넥션 대기·트랜잭션 시간이 병목 후보입니다.
- 다음 단계에서는 DB 호출 수, 커넥션 대기, MySQL slow query·락 대기를 관찰한 뒤 배치 저장 적용 여부를 검토합니다.

- 업로드 입력·부분 성공 응답: `ActivityUploadControllerIntegrationTest`
